# EveryDay_Food 菜单库接入评估

结论：可以补充买汰烧的候选菜谱，建议先筛选家常菜，完成字段转换与审核后入库。本次只做评估，未导入或覆盖现有菜谱。

核验日期：2026-11-15。固定版本：`5bd6cad753f68105a77b0ffcca2757f65fd5899d`。

直接检查了该版本的 [meals.json](https://github.com/Jiayu-zheng1/EveryDay_Food/blob/5bd6cad753f68105a77b0ffcca2757f65fd5899d/public/data/meals.json)，未运行对方项目代码。

| --- | --- | --- |
| 菜谱 | 1,093 条，ID 均唯一，家常菜 672 条 | 有足够的家常菜候选 |

| 与现有库重名 | 13 个，包括清蒸鲈鱼、番茄炒蛋等 | 不覆盖现有稳定 ID，先做版本对照 |
| 食材 | 7,507 条文字；1,030 道至少含一条不能直接按“名称＋数值＋现有单位”严格解析的食材 | 半根、勺、适量、复合调料等需保留原文并核对，不能默认作零 |
| 过敏原 | 全部未提供独立 allergens 字段 | 缺失不等于不过敏，需识别食材和复合调料后审核 |
| 营养 | 蛋白质、碳水、脂肪；无逐菜营养来源字段 | 可保留为来源方估算，不能直接作为本项目营养达标依据 |

上述 1,030 道表示存在解析工作，不表示菜谱不可用；调味料“适量”和一条鱼的可食部克数是不同问题，需要分别处理。

## 字段适配

对方的 [Meal 类型](https://github.com/Jiayu-zheng1/EveryDay_Food/blob/5bd6cad753f68105a77b0ffcca2757f65fd5899d/src/types.ts) 与现有数据并不相同：

- `name / steps / cuisine / methods / flavors` 可以保留；做法标签也便于后续选择蒸、炖、炒等动画。
- 对方 `category` 是家常、减脂、食疗等分类，需另外映射本项目的荤菜、蔬菜、主食、汤和早餐角色。
- `ingredients: string[]` 需转换成 `{name, amount, unit}`，同时保留原文。未明确用量的部分不能靠猜测补全。
- `servingSize.amount` 是一份的重量，不能直接填成我们的参考份数 `baseServings`。还需核对生重、熟重、整鱼与可食部等口径。
- `nutrition / per100g / kcal` 先保留来源及待核实状态。数学自洽不代表成分测定已核验，现有正向规则仍不能据此补齐钙、钠、纤维等缺失指标。

例如对方“清蒸鲈鱼”列出整鱼约 500 克、成品份量 300 克，并含蒸鱼豉油、料酒、油和红椒丝；现有版本按一参考份 180 克鲈鱼计算。这两个版本不能只按菜名合并。

## 许可与建议接入顺序

仓库使用 [MIT 许可证](https://github.com/Jiayu-zheng1/EveryDay_Food/blob/5bd6cad753f68105a77b0ffcca2757f65fd5899d/LICENSE)，复用时保留作者版权及许可证。README 另说明部分菜谱来自《老乡鸡菜品溯源报告》，后续应保留对应来源说明。

建议先选 30–50 道常用家常菜：保留来源仓库、固定版本、原始 ID 与原文；核对重复和食材单位；补充过敏原、口味和菜单角色；保存为草稿，确认后参与排菜。食疗名称或“减脂”等标签不自动转换为医疗规则。沿用当前菜单、采购和确认机制即可，无需迁移对方整套 React 应用。
